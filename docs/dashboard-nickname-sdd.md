# /dashboard 로그인 사용자 닉네임 표시 SDD

상태: 구현 완료, 브라우저 수동 확인 미완료  
작성일: 2026-10-27 (한국 시간)

## 1. 목표와 범위

- `/dashboard`의 인사말, 사이드바 계정 이름, 아바타 글자를 현재 로그인한 사용자의 닉네임으로 표시한다.
- 로그인, 새로고침, 계정 설정에서 닉네임 변경 후에도 같은 사용자 정보가 표시되어야 한다.
- 이번 변경은 화면 표시만 다룬다. 기록 예시 데이터, 할 일 체크, 라우팅 정책, 인증·DB·환경변수는 변경하지 않는다.

## 2. 현재 구조

- `App.jsx`가 `user`와 `loading` 상태를 소유한다.
- 로그인 성공 시 `/api/auth/login` 응답의 `user`를 `setUser`에 전달한다.
- 새로고침 시 저장된 토큰으로 `/api/auth/me`를 호출해 `user`를 복원한다.
- 계정 설정에서 `/api/auth/me/nickname` 성공 응답을 `setUser`에 전달한다.
- `/dashboard`는 `user`가 있을 때만 `DashboardPage`로 렌더링되지만, 현재 `user` prop을 전달하지 않는다.
- `DashboardPage.jsx`는 인사말 `이월님`, 계정 이름 `이월`, 아바타 `이`를 고정 표시한다.

## 3. 설계 결정

### 3.1 데이터 소유권과 흐름

`App`을 로그인 사용자 정보의 단일 출처로 유지한다. `DashboardPage`에서는 새 API 호출, 별도 사용자 상태, 닉네임 캐시를 만들지 않는다.

```text
로그인 응답 / 새로고침의 GET /api/auth/me / 닉네임 변경 응답
                         ↓
                   App.user 상태
                         ↓ user prop
                   DashboardPage
                         ↓
             인사말 · 계정 이름 · 아바타
```

### 3.2 컴포넌트 계약

`DashboardPage`의 입력을 `{ navigate, user }`로 확장한다. 이 경로는 인증된 `user`가 있을 때만 렌더링되므로 `user.nickname`을 그대로 사용한다. `user`가 없을 때를 위한 가짜 닉네임이나 Figma 예시 이름은 넣지 않는다.

`UserResponse`의 `nickname`은 서버에서 검증된 2~20자의 한글·영문·숫자·밑줄 문자열이다. 아바타에는 `user.nickname.slice(0, 1)`을 사용한다. 표시용 닉네임에 별도 저장이나 변환을 적용하지 않는다.

### 3.3 변경 위치

| 파일 | 변경 |
| --- | --- |
| `frontend/src/App.jsx` | `/dashboard` 분기에서 `DashboardPage`에 `user={user}` 전달 |
| `frontend/src/DashboardPage.jsx` | `user` prop 수신; 인사말, 사이드바 계정 이름, 아바타를 `user.nickname`으로 렌더링 |
| `frontend/src/DashboardPage.css` | 최대 길이 닉네임이 계정 영역을 넘칠 때에만 대시보드 전용 선택자로 말줄임/줄바꿈 보완 |

예상 렌더링은 다음과 같다. 실제 수정 시 기존 JSX 구조와 클래스 이름을 유지한다.

```jsx
<DashboardPage navigate={goTo} user={user} />

<span className="dashboard-avatar" aria-hidden="true">{user.nickname.slice(0, 1)}</span>
<strong>{user.nickname}</strong>
<h1>{user.nickname}님, 차곡차곡 쌓이고 있어요</h1>
```

## 4. 상태별 동작

| 상태 | 기대 동작 |
| --- | --- |
| 로그인 성공 | `App.user`에 로그인 응답이 저장되고 `/dashboard`에서 해당 닉네임 표시 |
| `/dashboard` 새로고침 | `loading` 화면 후 `/api/auth/me` 결과의 닉네임 표시 |
| 닉네임 변경 성공 | 계정 설정의 `setUser` 결과가 대시보드에 반영됨 |
| 닉네임 변경 실패 | 기존 `App.user` 유지; 대시보드에도 기존 닉네임 표시 |
| 토큰 없음 또는 사용자 조회 실패 | 기존 접근 제한에 따라 로그인 화면으로 이동; 예시 닉네임을 표시하지 않음 |

## 5. 화면과 접근성

- 인사말의 `h1`과 계정 설정 버튼의 의미·동작은 유지한다.
- 아바타 글자는 장식이므로 기존 `aria-hidden="true"`를 유지한다. 사용자 이름은 버튼의 텍스트로 읽을 수 있다.
- 사이드바의 고정 폭에서 긴 닉네임이 넘치면 이름 부분에만 `min-width: 0`, `overflow: hidden`, `text-overflow: ellipsis`, `white-space: nowrap`을 적용한다. 전체 닉네임을 확인할 수 있게 버튼의 접근 가능한 이름은 잘리지 않은 `user.nickname`을 포함해야 한다.
- 인사말은 이름 길이에 따라 줄바꿈을 허용하고, 화면 너비가 좁을 때 버튼·카드와 겹치지 않는지 확인한다.

## 6. 검증 계획과 완료 기준

1. 다른 닉네임을 가진 계정 두 개로 로그인해 세 표시 위치가 각각 계정에 맞는지 확인한다.
2. `/dashboard`에서 새로고침해 닉네임이 유지되는지 확인한다.
3. 계정 설정에서 닉네임을 변경한 뒤 `/dashboard`로 돌아와 새 이름과 새 아바타 글자를 확인한다.
4. 닉네임 변경 실패 시 이전 이름이 유지되는지 확인한다.
5. 토큰이 없는 상태에서 `/dashboard`가 기존처럼 `/login`으로 이동하는지 확인한다.
6. 최대 길이 닉네임으로 데스크톱과 모바일에서 겹침·가로 스크롤이 없는지 확인한다.
7. `frontend` 폴더에서 `npm.cmd run build`와 프로젝트 루트에서 `git diff --check`를 실행한다.

브라우저에서 계정 흐름을 검증할 수 없는 환경이라면 빌드 결과와 미확인 항목을 분리해 보고한다. 이 표시 변경만을 위해 백엔드 테스트나 새 프론트엔드 테스트 도구를 추가하지 않는다.

## 7. 진행 기록

- 완료: `App.user`를 대시보드에 전달하고 인사말·계정 이름·아바타를 닉네임으로 표시했다. 긴 닉네임을 위해 계정 이름 말줄임과 인사말 영역 축소를 대시보드 CSS에만 적용했다.
- 확인: 프론트엔드 빌드와 서로 다른 닉네임 두 개의 서버 렌더링 검사에서 세 표시 위치가 통과했다. `git diff --check`를 확인했다.
- 확인하지 못한 내용: 실제 브라우저의 로그인·새로고침·닉네임 변경·긴 닉네임 배치는 인증 가능한 세션으로 확인하지 못했다.
- 다음 할 일: 로그인 가능한 로컬 환경에서 6장의 브라우저 시나리오를 확인한다.
