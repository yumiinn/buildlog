# BuildLog MVP 개발 계획

## 1. 계획의 목적

이 문서는 [`spec.md`](spec.md)의 기능을 어떤 순서로 개발할지 설명합니다. 한 번에 Phase 하나만 진행하고, 자동 테스트와 직접 화면 확인을 통과한 뒤 다음 Phase로 넘어갑니다.

## 2. 개발 기준

- 화면은 **React**, API 서버는 **Python·FastAPI**로 만듭니다.
- 서비스 데이터는 **Supabase의 PostgreSQL**에 저장합니다. **SQLite3는 개발 중 자동 테스트용**으로 사용합니다. 두 데이터베이스에서 같은 기능이 동작해야 합니다.
- 데이터 저장 방식과 마이그레이션 도구는 Phase 0에서 FastAPI·PostgreSQL·SQLite3와 호환되는 것으로 정합니다. 한쪽에서만 통과한 테스트로 서비스 데이터베이스 동작을 단정하지 않습니다.
- 회원가입·로그인은 FastAPI에서 처리하고 Supabase는 PostgreSQL 데이터베이스로 사용합니다. 사용자가 보는 동작은 `spec.md`를 따릅니다.
- React 개발 화면은 Vite를 사용하고, 백엔드 데이터 저장은 SQLAlchemy 2.x·Alembic·psycopg 3 계열로 준비합니다. 정확한 패키지 버전은 Phase 1에서 설치 결과에 맞춰 고정합니다.
- 화면에서 버튼을 숨기는 것과 별개로 FastAPI에서도 읽기·수정·삭제 권한을 검사합니다.
- 비밀번호, 데이터베이스 연결 정보, 비밀 설정값을 코드나 문서 예시의 실제 값으로 넣지 않습니다. `.env.example`에는 이름과 설명만 둡니다.
- `.env`, `.venv`, `node_modules`, SQLite 파일, 로그와 생성 결과는 Git 기록 대상에서 제외합니다. Git 초기화와 커밋은 별도 요청 전까지 수행하지 않습니다.
- 이메일 확인, 비밀번호 찾기, 할 일 마감일·중요도·내 할 일 검색, 댓글 답글은 만들지 않습니다.

## 3. 예정된 프로젝트 구조

```text
buildlog/
├─ backend/
│  ├─ app/
│  │  ├─ main.py          # FastAPI 시작점
│  │  ├─ accounts/        # 회원가입, 로그인, 닉네임
│  │  ├─ records/         # 공부 기록, 할 일, 오류 기록
│  │  └─ community/       # 댓글, 좋아요, 신고
│  ├─ tests/
│  └─ requirements.txt
├─ frontend/
│  ├─ src/                # React 화면과 공통 컴포넌트
│  ├─ package.json
│  └─ public/
├─ database/              # 데이터 구조 변경 파일과 테스트용 SQLite 파일
├─ docs/
└─ .env.example           # 설정 이름만 기록
```

세부 파일명은 각 Phase에서 정하되, 위 역할과 `frontend`·`backend`·`database`·`docs` 폴더를 유지합니다.

## 5. Phase별 상세 계획

### Phase 0. 개발 시작 전 기준 확인

**목표:** 코드나 패키지를 변경하기 전에 문서, 도구, 데이터베이스 연결 방식을 확인합니다.

**작업**

1. `PRD.md`, `docs/spec.md`, 이 계획의 기능 범위와 제외 기능을 비교합니다.
2. 새 오류의 기본 상태는 미해결로 두고, 사용자가 처음부터 해결 상태를 선택할 때에는 해결 방법을 필수로 하는 규칙을 `spec.md`에 명확히 적습니다.
3. 회원가입·로그인은 FastAPI에서 처리하고 Supabase는 데이터베이스로 사용하는 기준을 문서에 반영합니다.
4. Python, Node.js, 패키지 관리 도구, SQLite3 사용 가능 여부를 읽기 전용 명령으로 확인합니다. FastAPI·React와 호환되는 버전은 개발을 시작할 때 선택합니다.
5. Supabase PostgreSQL 연결에 필요한 설정 이름, API와 React의 로컬 실행 주소, 테스트용 SQLite 파일 위치를 정합니다. 실제 비밀값은 문서에 적지 않습니다.
6. SQLAlchemy 2.x·Alembic을 데이터 저장·구조 변경의 기준으로 정하고, PostgreSQL과 SQLite3의 제약 조건 차이를 테스트 계획에 반영합니다.

**예상 변경 파일:** 필요하면 `docs/plan.md`, `docs/spec.md`, `docs/setup.md`만 수정합니다. 코드, 패키지, 데이터베이스는 아직 변경하지 않습니다.

**확인·완료 기준:** 문서의 충돌과 인증 방식이 정리되고, 실행 도구와 설정 항목을 알 수 있어야 합니다. 확인 결과는 [`phase0.md`](phase0.md)에 기록합니다.

### Phase 1. FastAPI·React 기본 구조 만들기

**목표:** 기능이 없는 API와 기본 화면을 실행하고 서로 연결합니다.

**작업**

1. `backend`의 Python 가상환경과 필요한 최소 패키지를 준비하고 버전을 기록합니다.
2. `backend/app/main.py`에서 FastAPI 서버를 실행하고 기본 상태 확인 응답을 만듭니다.
3. `frontend`에 Vite 기반 React 앱을 만들고 기본 화면을 표시합니다. 기본 화면에서 API 연결 상태를 확인합니다.
4. 로컬에서 React와 API가 통신할 수 있도록 개발 설정을 연결합니다. 인증과 공개 범위를 고려한 요청 설정은 Phase 0의 결정에 맞춥니다.
5. 설정값을 환경 변수에서 읽고 `.env.example`에 이름만 남깁니다. Supabase 연결 정보는 실제 값 없이 준비합니다.
6. SQLite 파일 등 생성 파일이 Git 기록 대상에서 제외되도록 `.gitignore`를 보완합니다. 아직 회원 데이터 구조나 실제 기능 화면은 만들지 않습니다.

**예상 변경 파일:** `backend/app/main.py`, 백엔드 의존성 파일, `frontend/package.json`, `frontend/src/`, `.env.example`, `.gitignore`.

**확인·완료 기준:** API와 React 개발 화면이 오류 없이 열리고 기본 연결을 확인할 수 있어야 합니다. 실제 비밀값이 파일에 기록되지 않아야 합니다.

### Phase 2. 사용자 데이터 구조와 데이터베이스 시작점

**목표:** 이메일로 식별되는 사용자를 안전하게 저장할 기반을 마련합니다.

**작업**

1. FastAPI가 사용하는 사용자 데이터를 정의합니다. 이메일과 닉네임은 필수·중복 불가이고, 닉네임은 2~20자·한글·영문·숫자·밑줄만 허용합니다.
2. 비밀번호 원문을 저장하지 않도록 안전한 저장 방식을 적용합니다.
3. PostgreSQL과 SQLite3에 같은 데이터 구조를 적용할 방법을 마련합니다. 테스트는 SQLite3로 실행하고, 서비스용 Supabase 연결과 구조 적용도 확인합니다.
4. 중복 이메일·닉네임, 허용 문자, 비밀번호 원문 노출 여부를 테스트합니다.
5. 저장 후 다시 읽고, 앱을 재시작해도 데이터가 남는지 확인합니다.

**예상 변경 파일:** `backend/app/accounts/`, `backend/app/`의 데이터베이스 연결 파일, 데이터 구조 변경 파일, `backend/tests/`, `database/`의 테스트 설정.

**확인·완료 기준:** 사용자 데이터 테스트가 통과하고 Supabase PostgreSQL에도 정한 구조를 적용·조회할 수 있어야 합니다. 실제 연결 정보는 환경 변수로만 사용합니다.

### Phase 3. 회원가입·로그인·닉네임 변경

**목표:** 사용자가 계정을 만들고 로그인하며 자기 닉네임을 바꿀 수 있게 합니다.

**작업**

1. FastAPI에 회원가입·로그인·닉네임 변경 처리와 서버 검증을 만듭니다.
2. React에 회원가입, 로그인, 계정 설정, 내 기록 홈 화면을 만듭니다.
3. 이메일 형식·중복, 비밀번호 8~64자, 닉네임 길이·문자를 검사합니다. 이메일·닉네임 앞뒤 공백을 제거합니다.
4. 가입 성공 후 로그인 화면, 로그인 성공 후 내 기록 홈으로 이동합니다.
5. 실패 시 `spec.md`대로 이메일·닉네임과 비밀번호의 유지·삭제 규칙을 화면에 반영합니다.
6. 로그인하지 않은 사용자의 기록 API와 화면 접근을 막습니다. 다른 사용자의 닉네임은 바꾸지 못하게 합니다.
7. 공개 기록과 댓글의 작성자 표시는 현재 닉네임을 읽도록 준비합니다.

**예상 변경 파일:** `backend/app/accounts/`, `backend/tests/`, `frontend/src/`의 회원·홈 화면과 API 호출 코드.

**확인·완료 기준:** `spec.md` 2장의 경계값·성공 화면·실패 시 입력 상태·권한 확인이 통과합니다. 이메일 확인과 비밀번호 찾기는 만들지 않습니다.

### Phase 4. 세 가지 기록의 데이터 구조

**목표:** 공부 기록, 할 일, 오류 기록을 저장할 구조를 만듭니다.

**작업**

1. 공부 기록에 작성자·제목·내용·공개 여부·작성/수정 시각을 둡니다.
2. 할 일에 작성자·제목·완료 여부·공개 여부·작성/수정/완료 시각을 둡니다.
3. 오류 기록에 작성자·오류 제목·내용·해결 방법·해결 여부·공개 여부·작성/수정/해결 시각을 둡니다.
4. 새 기록은 기본 비공개, 새 할 일은 미완료로 저장합니다. 새 오류는 상태를 따로 선택하지 않으면 미해결로 저장하고, 처음부터 해결을 선택하면 해결 방법을 필수로 검사합니다.
5. 길이 조건과 상태 전환을 서버와 저장 구조에서 검사하고, PostgreSQL과 SQLite3에 동일하게 적용할 수 있는지 확인합니다.
6. 완료 취소 시 완료 시각을 지우고, 오류를 미해결로 되돌릴 때 해결 방법을 유지하고 해결 시각을 지우는 동작을 테스트합니다.

**예상 변경 파일:** `backend/app/records/`, 데이터 구조 변경 파일, `backend/tests/`.

**확인·완료 기준:** 세 종류의 기록을 저장·재조회·재시작 후 재조회할 수 있고, 기본값과 상태 전환 테스트가 통과합니다. 아직 사용자 기능 화면은 만들지 않습니다.

### Phase 5. 공부 기록 기능 완성

**목표:** 만들기, 목록, 읽기, 검색, 수정, 삭제를 연결합니다.

**작업**

1. FastAPI에 공부 기록 처리와 작성자 권한 검사를 만듭니다. React에 작성·목록·상세·수정 화면을 연결합니다.
2. 제목 1~100자, 내용 1~5,000자, 앞뒤 공백 제거, 중간 띄어쓰기 유지 규칙을 적용합니다.
3. 내 목록을 최근 작성 순으로 보여주고 제목·내용 포함 검색을 제공합니다. 빈 검색어는 전체 내 목록을 보여줍니다.
4. 성공 후 목록 이동, 실패 시 입력·기존 데이터 유지, 수정 시각 표시, 삭제 확인을 구현합니다.
5. 작성자 외 사용자에게 읽기 범위와 수정·삭제 권한을 `spec.md`대로 제한합니다.

**예상 변경 파일:** `backend/app/records/`, `backend/tests/`, `frontend/src/`의 공부 기록 화면.

**확인·완료 기준:** `spec.md` 4장의 길이 경계값·정렬·검색·수정·삭제·권한 확인이 통과합니다.

### Phase 6. 할 일 기능 완성

**목표:** 만들기, 완료·취소, 필터, 수정, 삭제를 연결합니다.

**작업**

1. FastAPI와 React에 할 일 목록·작성·수정·삭제·완료 변경을 연결합니다.
2. 제목 1~100자와 공백 규칙을 적용하고 새 할 일은 미완료·비공개로 저장합니다.
3. 미완료 우선·같은 상태 최신순 정렬과 `전체`·`남은 일`·`완료한 일` 필터를 제공합니다.
4. 완료 시각 자동 저장과 취소 시 시각 삭제, 수정 시각 목록 표시, 성공 후 목록 이동, 실패 시 기존 값 유지를 구현합니다.
5. 작성자만 상태·제목·공개 여부를 바꾸거나 삭제하도록 서버에서 검사합니다. 삭제 전 확인을 보여줍니다.

**예상 변경 파일:** `backend/app/records/`, `backend/tests/`, `frontend/src/`의 할 일 화면.

**확인·완료 기준:** `spec.md` 5장의 경계값·필터·날짜·권한·삭제 취소 확인이 통과합니다. 내 할 일 검색, 마감일, 중요도는 만들지 않습니다.

### Phase 7. 오류 기록 기능 완성

**목표:** 오류 만들기, 해결 처리, 필터, 검색, 수정, 삭제를 연결합니다.

**작업**

1. FastAPI와 React에 오류 기록 목록·작성·상세·수정·삭제를 연결합니다.
2. 제목 1~100자, 내용 1~5,000자, 입력한 해결 방법 1~5,000자와 공백 규칙을 검사합니다.
3. 새 오류는 기본 미해결입니다. 처음부터 해결 상태를 선택할 수 있으나, 해결 상태로 저장할 때에는 해결 방법이 반드시 있어야 합니다.
4. `전체`·`미해결`·`해결` 필터, 최근 작성 순 정렬, 내 오류 제목·내용 포함 검색을 제공합니다.
5. 해결 시각 자동 저장, 미해결로 되돌릴 때 해결 방법 유지·시각 삭제, 수정 시각 상세 표시를 구현합니다.
6. 작성자만 변경·삭제하게 하고, 성공 후 목록 이동·실패 시 입력 유지·삭제 확인을 적용합니다.

**예상 변경 파일:** `backend/app/records/`, `backend/tests/`, `frontend/src/`의 오류 기록 화면.

**확인·완료 기준:** `spec.md` 6장의 입력 경계값·해결 방법 필수·상태 전환·검색·권한 확인이 통과합니다.

### Phase 8. 공개 범위·공개 기록·공개 검색

**목표:** 비공개를 보호하면서 로그인 사용자에게 공개 기록을 제공합니다.

**작업**

1. 세 종류 기록의 공개 여부는 작성자만 변경하게 합니다. 새 기록은 기본 비공개이며 변경 실패 시 기존 상태를 유지합니다.
2. React에 공개 기록 화면과 종류별 필터를 만들고 FastAPI에서 공개된 기록만 최근 작성 순으로 제공합니다.
3. 공개 공부 기록은 제목·내용, 공개 할 일은 제목, 공개 오류 기록은 오류 제목·내용·해결 방법으로 검색합니다. 빈 검색어는 공개 목록 전체를 보여줍니다.
4. 공개 기록의 현재 작성자 닉네임을 보여줍니다.
5. 비로그인 사용자와 다른 사용자가 비공개 기록을 목록·검색·직접 API 요청으로 볼 수 없도록 검사합니다.

**예상 변경 파일:** `backend/app/records/`의 공개 조회·권한 처리, `backend/tests/`, `frontend/src/`의 공개 기록 화면.

**확인·완료 기준:** `spec.md` 3·7장의 공개 전환·검색·필터·권한 확인이 통과하고, 비공개 기록이 한 건도 노출되지 않습니다.

### Phase 9. 댓글

**목표:** 공개 공부·오류 기록에서만 댓글을 사용하게 합니다.

**작업**

1. 댓글 데이터를 만들고 공개 공부 기록 또는 공개 오류 기록 하나에 연결합니다.
2. FastAPI에 댓글 작성·수정·삭제와 작성자·기록 작성자 권한 검사를 만들고 React 화면에 연결합니다.
3. 댓글 1~500자, 앞뒤 공백 제거, 오래된 댓글 먼저 보기, 삭제 확인을 적용합니다.
4. 기록이 비공개가 되면 기존 댓글을 유지하되 다른 사용자에게 숨기고, 다시 공개되면 보여줍니다.
5. 댓글 작성자의 현재 닉네임을 보여줍니다. 공개 할 일 댓글과 답글은 만들지 않습니다.

**예상 변경 파일:** `backend/app/community/`, 데이터 구조 변경 파일, `backend/tests/`, `frontend/src/`의 댓글 화면.

**확인·완료 기준:** `spec.md` 8장의 길이·공백·정렬·작성·수정·삭제 권한·비공개 전환 확인이 통과합니다.

### Phase 10. 좋아요

**목표:** 공개 공부·오류 기록에서 사용자당 기록 하나에 좋아요 하나만 남깁니다.

**작업**

1. 사용자와 대상 기록의 조합이 중복되지 않도록 저장 제약을 둡니다.
2. FastAPI에 처음 누르면 저장, 다시 누르면 취소하는 처리를 만들고 React에서 현재 상태와 전체 개수를 보여줍니다.
3. 처리 실패 시 기존 상태·개수를 유지합니다. 공개 할 일에는 좋아요 처리와 화면을 만들지 않습니다.
4. 기록이 비공개가 되면 좋아요를 유지하되 다른 사용자에게 숨기고, 다시 공개되면 보여줍니다.

**예상 변경 파일:** `backend/app/community/`, 데이터 구조 변경 파일, `backend/tests/`, `frontend/src/`의 좋아요 표시·버튼.

**확인·완료 기준:** `spec.md` 9장의 등록·취소·중복 차단·개수·권한 확인이 통과합니다.

### Phase 11. 신고와 운영자 확인

**목표:** 공개 기록·댓글 신고를 저장하고 운영자만 내용을 확인하게 합니다.

**작업**

1. 신고 대상을 공개 공부 기록·할 일·오류 기록 또는 댓글 하나로 제한합니다.
2. 신고 이유 1~500자·앞뒤 공백 제거, 같은 사용자의 같은 대상 중복 신고 금지를 저장 구조와 FastAPI에서 검사합니다.
3. React에 신고 입력·성공·실패 안내를 연결합니다. 실패하면 신고 이유를 남기고, 신고만으로 대상을 자동 삭제하지 않습니다.
4. 운영자만 신고 목록·내용을 확인할 수 있는 최소 화면과 API를 만듭니다. 일반 사용자 접근은 차단합니다.
5. 대상이 비공개가 되어도 운영자가 기존 신고를 확인할 수 있게 유지합니다. 신고 처리 상태 기능은 만들지 않습니다.

**예상 변경 파일:** `backend/app/community/`, 데이터 구조 변경 파일, `backend/tests/`, `frontend/src/`의 신고 입력·운영자 확인 화면.

**확인·완료 기준:** `spec.md` 10장의 입력 경계값·중복 차단·자동 삭제 없음·운영자 권한 확인이 통과합니다.

### Phase 12. 반응형 화면과 공통 실패 처리

**목표:** 컴퓨터와 휴대폰에서 모든 기능을 읽고 조작할 수 있게 정리합니다.

**작업**

1. React 공통 컴포넌트와 CSS에서 밝은 배경, 읽기 쉬운 카드, 메뉴·버튼·입력칸·실패 안내를 통일합니다.
2. 너비 360px 이상의 화면에서 글과 버튼이 겹치거나 화면 밖으로 나가지 않게 조정합니다.
3. Chrome·Edge·Safari 최신 두 버전에서 주요 흐름을 확인합니다.
4. 저장·수정·삭제·조회 실패 시 입력과 기존 데이터가 `spec.md`대로 유지되는지 다시 확인합니다.
5. 권한 없는 버튼을 숨기되 FastAPI 권한 검사도 유지합니다. 범위 밖 기능을 암시하는 버튼이나 메뉴를 제거합니다.

**예상 변경 파일:** `frontend/src/`의 공통 화면·스타일, 관련 화면 테스트, 필요한 범위의 API 오류 처리.

**확인·완료 기준:** `spec.md` 11장의 화면 크기·브라우저·동일한 데이터와 권한 확인이 통과합니다.

### Phase 13. 전체 통합 확인과 실행 문서

**목표:** 처음 설치하는 사람도 실행할 수 있고 모든 기능이 함께 동작하는 상태로 마무리합니다.

**작업**

1. SQLite3를 사용하는 백엔드 자동 테스트와 프론트엔드 테스트를 실행합니다.
2. Supabase PostgreSQL 연결과 데이터 구조 적용 및 주요 저장·조회 흐름을 확인합니다. SQLite3에서만 통과하는 데이터 동작이 없도록 점검합니다.
3. 사용자 A·사용자 B·운영자 권한 시나리오를 확인합니다. 목록·검색·직접 API 요청에서 비공개 기록이 노출되지 않아야 합니다.
4. 프로그램을 종료하고 다시 실행해 저장 데이터가 남는지 확인합니다.
5. `spec.md`의 기능별 확인 항목과 `PRD.md`의 첫 버전 완료 목록을 모두 점검합니다. 실패한 항목만 고칩니다.
6. Python·Node.js 준비, 의존성 설치, 환경 변수, Supabase 연결, 테스트용 SQLite3, API·React 실행, 테스트 명령을 `docs/setup.md`에 적습니다.
7. `.env.example`에 실제 비밀값이 없고 `.env`·SQLite 파일 등이 Git 기록 대상에서 제외되는지 확인합니다.

**예상 변경 파일:** `docs/setup.md`, `docs/README.md`, `.env.example`, 테스트와 필요한 기존 코드.

**완료 기준:** 모든 자동 테스트와 `spec.md` 확인 항목이 통과하고, 컴퓨터·휴대폰에서 주요 기능을 사용할 수 있으며, 문서만 보고 실행할 수 있습니다.

## 6. 실제 진행 방법

1. 첫 작업은 Phase 0만 진행합니다.
2. Phase 0의 환경·문서 확인 결과와 사용자 결정이 필요한 항목을 공유합니다.
3. Phase 0이 정리된 뒤 Phase 1만 진행합니다. 이후에도 같은 방식으로 한 Phase씩 진행합니다.
4. 여러 Phase를 한 번에 구현하지 않고, 실패한 확인 항목은 해당 Phase에서 해결합니다.
